## 한눈에 보기

- 이 단계는 앱을 만들기 전의 준비 단계예요. 세 가지를 확인했어요. 어떤 문서를 기준으로 삼을지, 최신 도구를 어떻게 설치할지, 예전 버전(방꾸미 1.0)에서 무엇을 고칠지예요.
- 문서들이 한 서비스의 문서가 아니라 **서로 다른 두 서비스의 문서**라는 것을 찾았어요. 그래서 "직접 말한 요청이 먼저, 그다음 최신 문서"라는 순서를 정했어요.
- 조사 6개를 동시에 진행했어요. 화면 도구는 임시 폴더에 실제로 설치해서 빌드(배포용 파일 만들기)와 테스트(자동 검사)가 통과하는 것까지 확인했어요.
- 방꾸미 1.0의 계산 프로그램을 직접 돌려서, 100점 점수제가 좋은 배치와 맞지 않는 예를 확인했어요.
- 결과물은 결정 기록(`docs/DECISIONS.md`)과 구조 설명(`docs/ARCHITECTURE.md`)이에요. 문서끼리 어긋난 곳 35건, 명세서의 빈칸 68건을 찾았어요.

> **문서 15개의 구성**
> 방꾸미 2.0 문서 5개는 14시 2분에, '온라인 모델하우스' 문서 4개는 15시 13분에 저장됐어요. 나머지 6개는 그 4개가 가리키는 바탕 문서예요(14시 25분부터 57분 사이 저장). 이 6개는 작업용으로 전달받은 문서가 아니에요. 어떤 서비스의 문서인지 확인하려고 읽기만 했어요. 시각은 파일이 PC에 저장된 때라서, 내용을 정한 때와는 다를 수 있어요.

**설치해서 확인한 버전**: Vite 8.3, React 19.3, TypeScript 7.0, Tailwind CSS 4.3, three.js 0.187. 본 프로젝트의 `package.json`도 같은 버전대예요.

**방꾸미 1.0의 계산 프로그램을 직접 돌려서 본 것**

- 모든 가구를 벽에서 30cm씩 띄운 어색한 배치도 75점이 나왔어요.
- 침대 머리가 창 아래에 있어도 4점만 깎였어요.
- 끌기 격자(5cm) 때문에 생긴 3cm 겹침이 빨간 오류로 나왔어요.
- 침대 옆에 서랍장을 딱 붙이면 경고가 떴어요.

**방꾸미 1.0의 코드와 기록을 읽어서 본 것**

- 가구를 추가하면 배치를 처음부터 다시 계산해서, 손으로 맞춘 배치가 사라졌어요.
- 크기 조절 손잡이는 그림만 있고 동작하지 않았어요.
- AI는 개발자 PC에 깔린 프로그램을 불러 쓰는 방식이었어요. 그래서 공개 주소에서는 AI가 동작하지 않았어요. 1.0 기록에 남은 응답 시간은 한 번에 10초에서 77초였어요(이번에 다시 재지는 않았어요).

## 중요한 결정과 이유

**1. 사용자가 직접 말한 것이 먼저, 그다음 최신 문서**
나중에 저장된 문서 4개는 다른 제품(대구 미분양 아파트를 지도로 보여 주는 서비스)의 문서였어요. 방꾸미는 그 안의 한 단계(S4 가구 배치)에 해당해요. "최신 문서 우선"을 그대로 적용하면 직접 요청한 구성(Vite, React, Tailwind, three.js, Capacitor, Vercel 서버 함수)과 어긋나요.

- 받아들인 것: 화면 코드는 TypeScript로 쓰기, 작업 보고를 "실행 방법 + 다음 할 일 3개"로 끝내기, 점수 대신 3단계 피드백 유지.
- 받아들이지 않은 것: FastAPI(파이썬으로 서버를 만드는 도구) 서버, frontend/backend 폴더 나누기, 서비스 이름 바꾸기. 다른 제품의 것이라서예요.

**2. 화면은 TypeScript, 계산·자료·서버는 JavaScript에 타입 검사 붙이기**
계산 코드를 서버와 브라우저와 테스트가 변환 없이 같이 쓸 수 있어요. 타입 검사는 자료 약속(`SCHEMA.md`)과 다른 필드 이름을 빌드할 때 잡아 줘요.

**3. 좌표 약속을 먼저 정하기**
방 왼쪽 위가 (0, 0)이에요. 가구 좌표는 돌린 뒤 바닥에서 차지하는 네모의 왼쪽 위예요. 회전 0일 때 정면은 아래쪽이고, 침대 머리는 뒤쪽이에요. `SCHEMA.md`에는 "방 왼쪽 위가 기준"이라는 것만 있고, 가구를 돌렸을 때의 기준점과 정면 방향은 없었어요. 그대로 두면 2D, 3D, 계산이 서로 다르게 해석할 위험이 있었어요. 이 계산은 `src/engine/geometry.js` 한 곳에만 둬요.

**4. AI 키는 서버 환경변수에만 두기**
키가 화면 코드에 들어가면 누구나 볼 수 있어요. 지금은 키가 없어서 AI 대신 규칙으로 만든 기본 답이 나와요. 구독 로그인 방식의 AI는 본인용이라 공개 서비스에 붙이지 않아요.

**5. 공개 주소는 새로 만들고, 버전은 하나만**
1.0의 주소와 저장소를 다시 쓰지 않아요. 내 PC 전용 버전도 따로 두지 않아요. 1.0에서 "내 PC에서만 되는 기능"이 공개 주소에서는 동작하지 않았기 때문이에요.

**6. 스케치업 내보내기는 .skp 대신 .dae**
스케치업이 열 수 있는 .dae 파일을 서버 없이 브라우저에서 만들기로 했어요. .skp를 만드는 스케치업 공식 도구는 윈도우와 맥에서만 돌아가는 것으로 알고 있어서, Vercel 서버에서는 쓸 수 없다고 판단했어요. 이 부분은 공식 문서로 다시 확인하지는 않았어요. 내보내기 기능 자체는 아직 만들지 않았어요.

**7. 폴더 이름은 영어(bangkkumi2)**
안드로이드 빌드 도구 안에, 윈도우에서 폴더 경로에 영어가 아닌 글자가 있으면 멈추는 검사가 들어 있는 것을 확인했어요. 실제로 앱을 빌드해서 본 것은 아니에요.

**8. 한글 PDF 보고서는 Edge 브라우저로 만들기**
PC에 깔린 Edge를 화면 없이 실행해서 인쇄해요. 이 보고서도 그 방법으로 만들었고, 한글이 깨지지 않는 것을 확인했어요.

## 심사위원 예상 질문과 답

**질문 1. 왜 바로 만들지 않고 조사부터 했나요?**
저희가 확인한 문서가 15개였고 서로 말이 다른 곳이 있었어요. 그대로 만들면 중간에 다시 만들어야 할 수 있어서, 먼저 어느 문서를 따를지 정했어요. 어긋난 곳 35건은 표로 정리해서 `docs/DECISIONS.md`에 결정과 이유를 적어 두었어요.

**질문 2. 문서가 서로 다를 때 무엇을 기준으로 정했나요?**
저희가 직접 말한 요청을 가장 먼저 두고, 그다음에 더 나중 문서를 따랐어요. 나중 문서 4개는 다른 서비스용이어서 전부 따르지는 않았어요. 방꾸미에 그대로 쓸 수 있는 규칙, 예를 들어 TypeScript 사용과 보고 형식만 가져왔어요.

**질문 3. 왜 점수를 쓰지 않나요?**
점수를 없애는 것은 방꾸미 2.0 기획 문서에 처음부터 있던 원칙이에요. 저희는 이 단계에서 1.0 계산 프로그램을 직접 돌려 그 근거를 확인했어요. 가구를 전부 벽에서 30cm 띄운 배치도 75점이 나왔고, 침대 머리가 창 아래에 있어도 4점만 깎였어요. 그래서 점수 대신 확실한 문제, 개선 제안, 취향별 배치안의 세 단계로 알려 주는 방식을 유지했어요.

**질문 4. 최신 도구들이 함께 잘 돌아가는지 어떻게 확인했나요?**
저희는 임시 폴더에 Vite 8.3, React 19.3, TypeScript 7.0, Tailwind CSS 4.3, three.js 0.187을 실제로 설치했어요. 거기서 빌드와 테스트가 통과하는 것을 본 다음에 본 프로젝트를 시작했어요.

**질문 5. AI는 지금 실제로 동작하나요?**
아직 아니에요. AI API 키가 없어서 지금은 규칙으로 만든 기본 답이 나와요. 키는 서버 환경변수에서만 읽도록 만들어 두었어요. 다만 실제 키를 넣고 시험해 보지는 못했어요. 이미지 생성 AI는 어느 회사 것을 쓸지 아직 정하지 않았어요.

**질문 6. 휴대폰 앱으로도 나오나요?**
이 단계에서는 Capacitor라는 포장 도구를 조사만 했어요. 임시 폴더에서 설치와 초기 설정은 해 봤지만, 실제 앱 파일을 만들거나 휴대폰에서 돌려 보지는 않았어요. 본 프로젝트 설치는 중간점검 뒤로 미뤘어요.

**질문 7. 좌표 약속을 왜 따로 정했나요?**
자료 약속 문서에 가구를 돌렸을 때의 기준점과 정면 방향이 적혀 있지 않았어요. 2D 화면, 3D 화면, 계산이 각자 다르게 해석하면 가구가 엉뚱한 곳에 그려져요. 그래서 한 가지로 정하고 계산을 한 파일에만 두었어요.

## 아직 안 된 것과 다음 단계

**아직 안 된 것**

- Capacitor는 조사만 했어요. 본 프로젝트 설치, 앱 파일 만들기, 휴대폰 확인은 아직 안 했어요.
- AI API 키가 없어요. AI 기능은 기본 답으로만 동작해요.
- 이미지 생성 AI는 어느 회사 것을 쓸지 정하지 않았어요.
- 15시 13분 문서 4개가 다른 서비스용이라는 판단은 조사 결과예요. 지금 방향(방꾸미 2.0을 따로 만들기)이 맞는지는 프로젝트 주인의 확인이 남아 있어요.
- 명세서 빈칸 68건을 모두 정한 것은 아니에요. 정한 것은 `docs/DECISIONS.md` 3장, 물어볼 것은 5장에 있어요.
- Vercel 무료(Hobby) 요금제 한도와 요청 크기 한도(4.5MB)는 공식 문서로만 확인했어요.

**실행 방법**

- 개발용으로 열기: 프로젝트 폴더에서 `npm install` 다음 `npm run dev`
- 한 번에 검사하기: `npm run verify` (테스트, 빌드, 비밀값 검사를 차례로 해요)
- 이 보고서를 PDF로 만들기: `npm run report -- reports/1단계_조사와_계획.md`

**다음 할 일 3개**

1. 정한 좌표 약속대로 계산 프로그램과 2D 화면을 만들고 테스트로 확인하기.
2. AI API 키를 언제 넣을지, 이미지 생성 AI를 어느 회사 것으로 할지 정하기.
3. 중간점검 뒤에 Capacitor를 설치하고 실제 휴대폰에서 확인하기.

## 용어 풀이

- **빌드 / 테스트**: 빌드는 코드를 인터넷에 올릴 파일로 바꾸는 일, 테스트는 결과가 맞는지 자동으로 검사하는 일이에요.
- **Vite / React**: Vite는 화면 코드를 실행하고 빌드해 주는 도구, React는 화면을 부품 단위로 만드는 도구예요.
- **TypeScript / 타입 검사**: JavaScript에 "이 값은 숫자, 이 값은 글자" 같은 종류 표시를 붙인 언어예요. 종류가 틀리면 실행 전에 알려 줘요.
- **Tailwind CSS / three.js**: 색과 간격 같은 꾸밈을 붙이는 도구, 브라우저에서 3D를 그리는 도구예요.
- **Capacitor**: 웹사이트를 휴대폰 앱으로 포장해 주는 도구예요.
- **Vercel / 서버 함수**: Vercel은 웹사이트를 올려 주는 서비스예요. 서버 함수는 요청이 올 때만 잠깐 실행되는 작은 서버 코드예요.
- **API 키 / 환경변수**: API 키는 AI 서비스를 쓸 때 내는 비밀번호 같은 값이에요. 환경변수는 코드 밖 서버 설정에 넣어 두는 값이에요.
- **명세서(SPEC) / 자료 약속(SCHEMA)**: 무엇을 만들지 적은 문서와, 자료의 이름과 모양을 정한 문서예요.
- **커밋 / 커밋 신원**: 커밋은 코드를 저장소에 기록하는 일이에요. 커밋 신원은 그때 남는 이름과 메일 주소예요.
- **.dae / .skp**: 3D 모델 파일 형식이에요. .skp는 스케치업 전용, .dae는 여러 프로그램이 열 수 있는 형식이에요.
- **끌기 격자**: 가구를 끌 때 5cm 단위로 딱딱 맞춰지게 하는 기능이에요.
