## 한눈에 보기

- 목적은 **올린 사이트를 실제로 눌러 보고 여러 관점으로 검토해 문제를 찾고**, 심사에서 걸릴 만한 것부터 고쳐 다시 올리는 것이었어요.
- 네 가지 검토(화면, 규칙·보안, 명세, 계산)에서 문제 **52건**을 찾았어요(화면 20건, 계산 25건, 서버 7건). 그중 '막는 문제'는 6건이었어요. 5건은 코드를 고쳤고, 1건은 공개 사이트가 최신 코드보다 뒤처졌던 것이라 다시 올렸어요.
- 52건 중 **34건에 고친 기록**이 있어요(한 부분만 고친 것도 들어 있어요). 나머지 18건은 설정으로 해결했거나, 받아들이지 않았거나, 미뤘어요.
- 같은 단계에서 **AI 키를 서버에 연결**했고, **리포트 기능 두 가지**(가족·사용자용 리포트, 업체·시공용 사양서)를 넣었어요.
- 자동 검사(코드로 계산 결과를 확인하는 검사)는 126개에서 **160개**로 늘었고 모두 통과해요. 2026-11-26 17:25에 다시 올렸어요. 다만 고친 뒤 다시 확인하지 못한 것이 있어서 아래에 그대로 적었어요.

## 중요한 결정과 이유

**1. 벽은 문제도 제안도 만들지 않아요.**
침대 발치를 벽에 붙이면 빨간 문제가 뜨고, 벽·협탁·침대를 딱 붙여도 통로 제안이 떴어요. 명세서 2.1에는 "다른 가구가 막고 있음"이라고 적혀 있어서, 벽 때문에는 아무 말도 하지 않게 고쳤어요. "아이 모서리 규칙도 벽과의 좁은 길을 봐야 한다"는 의견은 이 결정과 부딪혀서 받아들이지 않았어요.

**2. '갈 길이 없음'은 30cm 폭으로도 못 갈 때만 확실한 문제예요.**
60cm 폭으로만 못 가면 개선 제안으로 내요. 명세서 글자대로면 60cm 실패가 문제지만, 60cm는 참고값(법적·안전 기준 아님)이에요. 그대로 하면 협탁 옆처럼 정상인 배치가 빨간 문제가 돼요. 확실한 문제는 정말 확실할 때만 내기로 했고, `docs/DECISIONS.md`에 적었어요.

**3. 배치안은 5개보다 적게 나올 수 있어요.**
책상이 없는 방에 '창가 워크스페이스형'이 나왔어요. 그 테마에 필요한 가구가 없으면 테마를 빼기로 했어요. 개수를 채우는 것보다 틀린 설명을 안 하는 쪽을 골랐어요. 가구를 다 놓은 안이 하나라도 있으면 못 놓은 안도 내지 않아요.

**4. AI를 너무 많이 부르면 오류 대신 기본 답을 줘요.**
한 주소에서 10분에 30번을 넘으면 규칙으로 만든 기본 답으로 바꿔요. 오류 화면을 보여 주면 시연이 끊기기 때문이에요. 다른 사이트에서 오는 요청은 거절(403)해요.

**5. API 키는 서버 설정과 PC의 Git 제외 파일에만 넣었어요.**
서버 설정은 Vercel(사이트를 올린 서비스)의 비밀값 칸이고, PC 쪽은 Git(코드 변경 기록 도구)에 올라가지 않게 제외해 둔 `.env.local` 파일이에요. 화면 코드, 보고서, 저장소에는 넣지 않았어요. 올릴 파일에 키나 개인 경로가 섞였는지 보는 검사도 통과했어요.

**6. 취향 문제는 고치지 않고 남겼어요.**
스크롤바 모양, 시작 화면 그림, 2D 도면 그림체 3건은 디자인 선택이라 손대지 않았어요. 가격 표시도 지금 문구('시연용 예상 가격')가 더 정직해서 그대로 뒀어요.

**7. 눌러 보는 검사를 만드는 작업을 중간에 멈췄어요.**
이 작업이 30분 넘게 끝나지 않아 고치는 단계 전체가 막혔어요. 그래서 작업을 멈추고, 그때까지 만들어진 스크립트를 최종 확인 단계에서 돌리는 방식으로 바꿨어요.

## 심사위원 예상 질문과 답

**Q1. 검토는 어떻게 했나요?**
저희는 다섯 가지를 동시에 했어요. 프로그램이 브라우저를 직접 조작하는 검사, 규칙·보안 검토, 명세 대조, 방 24종에서 배치 252개를 만들어 보는 계산 검토, 화면 약 120장 캡처 검토예요. 뒤의 네 가지 검토에서 문제 52건을 찾았어요.

**Q2. 찾은 문제를 다 고쳤나요?**
아니요. 저희는 심사에서 바로 걸릴 6건을 먼저 다뤘고, 52건 중 34건에 고친 기록이 있어요. 나머지는 설정으로 해결한 것 2건, 받아들이지 않은 것 6건, 미루거나 다른 항목에 묶인 것 10건이에요.

**Q3. 벽에 붙인 가구는 왜 아무 말도 안 하나요?**
저희는 벽이나 가구에 딱 붙인 배치는 사용자가 일부러 한 것으로 봐요. 검토에서 이 원칙이 깨지는 경우를 찾았고, 벽 때문에는 문제도 제안도 내지 않게 고쳤어요. 다른 가구가 서랍 앞이나 의자 자리를 막을 때만 알려 줘요.

**Q4. 통로 60cm는 어디서 나온 기준인가요?**
60cm는 참고값이고 법적·안전 기준이 아니에요. 그래서 저희는 60cm로 못 가는 경우는 개선 제안으로만 내고, 30cm로도 못 갈 때만 확실한 문제로 내요.

**Q5. AI 키가 밖으로 새거나 요금이 많이 나올 위험은 없나요?**
키는 서버 설정과 PC의 Git 제외 파일에만 두었고 화면 코드에는 넣지 않았어요. 다른 사이트에서 오는 요청은 거절하고, 한 주소에서 10분에 30번을 넘으면 기본 답으로 바꿔요. 다만 이 횟수 제한은 간단한 방식이고 요금 상한은 아직 없어서, AI 회사 설정 화면에서 한도를 거는 것이 남은 일이에요.

**Q6. 리포트는 왜 두 가지인가요?**
보는 사람이 달라서예요. 가족·사용자용은 평면도 그림, 3단계 피드백, 가구 목록, 비용 요약이 들어가요. 업체·시공용 사양서는 방 치수표, 문·창문 표, 가구별 치수와 좌표, 마감재 색이 들어가고 표 복사와 인쇄가 돼요. 리포트 안 3D 그림은 아직 없어서 화면에 '준비 중'이라고 적었어요.

**Q7. 고친 뒤에 다시 확인했나요?**
자동 검사 160개는 마지막 코드로 모두 통과했어요. 눌러 보는 검사는 고친 뒤 PC에서 37개 모두 통과했어요. 휴대폰 쪽은 고친 뒤 다시 돌리지 못했어요. 처음 실패한 2개가 PC와 같은 문제(복사한 의자가 책상과 겹침)였다는 것까지만 확인했어요.

## 아직 안 된 것과 다음 단계

**화면에서 보이는 것**

- 휴대폰 폭에서 좁은 가구의 이름표가 잘려요(옷장이 "800…"으로 보이고 책장·의자는 이름이 없어요).
- 예시 방의 배치안 5개가 서로 비슷해 보여요. 수납형에서는 침대가 벽 구석에 붙지 않아요.
- 예시 방의 콤팩트형 배치안에 통로 제안 1건(옷장 앞 약 40cm)이 붙어 나와요. 문제가 아니라 제안이에요.
- 예시 방의 수납 침대 발치에 다른 가구를 붙이면 확실한 문제로 나와요(그 침대만 서랍용 앞 공간 50cm가 있어서예요).
- 한 변이 10m 이상인 큰 방에서는 자동 배치가 0.3초를 넘어요(15m×15m에서 약 0.79초).
- 피드백 칸에서 참고값 안내 문구가 제안이 있을 때만 나와요(리포트 쪽은 고쳤어요).
- 휴대폰을 가로로 돌리면 평면도가 아주 작아진다는 발견은 고친 기록이 없어요. 시연은 세로로 해요.

**고친 뒤 다시 확인하지 못한 것**

- 공개 주소에서 [전체 다시 추천]을 다시 눌러 보는 것(최신 코드로 다시 올리기만 했어요)
- 휴대폰 쪽 눌러 보는 검사와 실제 휴대폰 터치(크기 흉내로만 봤어요), 2D·3D 10번 바꾸기(3번만 돌렸어요)
- 스타일과 글로 가구 추가에서 같은 안내가 두 번 나오던 것(코드는 고쳤지만 화면으로 다시 보지 못했어요)
- 합친 뒤 업체·시공용 사양서 전환 버튼 클릭(리포트를 만든 단계에서는 확인했어요)
- 실제 브라우저에서 표 복사가 성공하는 경우(자동 브라우저에서는 복사가 막혀 대체 안내만 봤어요)
- 빌드한 사이트에서 인터넷이 끊긴 상태의 3D(개발용 서버에서만 확인했어요)

**미룬 것과 한계**

- 고치기 작업 보고에 '미룸'으로 적힌 항목은 모두 30개예요(발견 52건 밖의 뒷정리 항목도 포함).
- 소파와 TV장이 서로 마주 보지 않아요. 높은 책장이 창문 절반을 가릴 수 있어요.
- AI 호출 수 제한은 서버 인스턴스마다 따로 세는 간단한 방식이에요. 요금 상한은 없어요.
- 리포트 안 3D 그림이 없어요. `docs/ARCHITECTURE.md`에 리포트 파일이 아직 적혀 있지 않아요.
- 눌러 보는 검사 안의 AI 버튼은 유료 호출을 피하려고 키를 비운 서버에서 기본 답으로만 봤어요.

**다음 할 일 3개**

1. 시연 전에 실제 휴대폰과 실제 브라우저로 위 '다시 확인하지 못한 것'을 한 번씩 눌러 봐요.
2. AI 회사 설정 화면에서 요금 한도를 걸어요.
3. 휴대폰 이름표 잘림과 예시 방 배치안이 비슷한 문제를 고쳐요.

## 용어 풀이

- **눌러 보는 검사(e2e)**: 프로그램이 브라우저를 사람처럼 눌러 보며 화면이 제대로 움직이는지 확인하는 검사예요.
- **자동 검사(테스트)**: 계산 결과가 맞는지 코드로 확인하는 검사예요. `npm test`로 돌려요.
- **명세(SPEC)**: 무엇을 만들지 적어 둔 약속 문서예요.
- **검사기**: 배치를 보고 확실한 문제, 개선 제안, 좋은 점을 찾아 주는 계산 부분이에요.
- **막는 문제**: 고치지 않으면 심사에서 바로 걸릴 만큼 큰 문제예요.
- **빌드**: 코드를 인터넷에 올릴 파일로 묶는 작업이에요.
- **API 키**: AI 서비스를 쓸 때 내는 비밀번호 같은 값이에요. 쓴 만큼 요금이 나가요.
- **출처**: 요청을 보낸 사이트의 주소예요. 우리 사이트가 아니면 거절해요.
- **403 / 200**: 서버의 답 번호예요. 403은 "거절", 200은 "정상"이에요.
- **기본 답**: AI를 못 쓸 때 정해 둔 규칙으로 만드는 답이에요.
- **서버 인스턴스**: 요청을 처리하려고 그때그때 켜지는 서버 한 대예요. 여러 대가 켜지면 횟수를 따로 세요.
- **참고값**: 편하게 쓰기 위한 어림 기준이에요. 법적·안전 기준이 아니에요.
- **사양서와 좌표**: 사양서는 업체가 시공할 때 보는 치수·재료 목록이고, 좌표는 가구 위치를 숫자로 적은 것이에요.
